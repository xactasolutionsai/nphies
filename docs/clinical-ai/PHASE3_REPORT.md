# المساعد السريري — تقرير المرحلة الثالثة (2026-09-26)

نطاق المرحلة: تحسين التشغيل والأداء والتكامل، ثم التقييم اللغوي والسريري المستقل.

- لم يُحمَّل أي نموذج. حُمّلت شيفرة مكتبة OpenMed 2.3.0 فقط (ملف wheel بلا نماذج) لقراءة طريقة التحميل.
- لم يُفعَّل Ollama، ولم يُرسل شيء إلى نفيس، ولم تُعدَّل بيانات مرضى.

> **لم تُقَس أرقام أداء حقيقية ولم يُجرَ تقييم سريري مستقل.** كلاهما يحتاج النموذج مثبتاً على عتاد المستشفى، ونصوصاً يوسمها مختصون. ما أُنجز: إصلاح مصادر البطء والتعطل في الكود، وأداة قياس وعُدّة تقييم جاهزتان ومختبرتان. كل رقم أداء في هذا التقرير **محاكى** لغرض التحقق من الأداة فقط.

## 1. ما وُجد قبل التعديل (موثّق من الكود)

| المشكلة | الدليل | الأثر المتوقع |
|---|---|---|
| **إعادة تحميل النموذج لكل نافذة نص في كل طلب** | `worker.py` السابق كان يستدعي `analyze_text` لكل نافذة 256 رمزاً دون تمرير `loader`. في شيفرة OpenMed 2.3.0، تنشئ `analyze_text` كائن `ModelLoader` جديداً ما لم يُمرَّر لها واحد (`openmed/__init__.py`)، والتخزين المؤقت للنموذج داخل الكائن نفسه (`core/models.py`: `self._pipelines`). | زمن يتضاعف مع طول النص وعدد الطلبات. **لم يُقَس** لغياب النموذج |
| عملية Python جديدة لكل طلب | `inference.js` السابق: `spawn` لكل تحليل | بدء بارد في كل طلب |
| تحليل واحد لكل عملية Node، وأي طلب ثانٍ يُرفض فوراً | متغير `busy`، ويعيد 429 | لا طابور ولا عدالة بين المستخدمين |
| لا إلغاء عند مغادرة المستخدم، ولا منع لتكرار الإرسال، ولا حد للطلبات | `routes.js` السابق | عمل ضائع وسجلات مكررة |
| لا وسيلة لمعرفة أن النسخة المنشورة هي المختبرة | — | لا يمكن ربط نتيجة تقييم بنسخة منشورة |

## 2. التغييرات الفعلية

| الملف | الوظيفة |
|---|---|
| `backend/openmed/worker.py` | عامل دائم ببروتوكول أسطر JSON: كائن `ModelLoader` واحد لكل عملية يُمرَّر لكل استدعاء، ومحلّل رموز محفوظ لكل وضع، وتحميل مسبق اختياري (`OPENMED_PRELOAD`)، وأزمنة المعالجة داخل الاستجابة. رموز الأخطاء لا تحمل نصاً سريرياً. البروتوكول مفصول عن تشغيل النموذج ليُختبر دونه. |
| `backend/openmed/workerPool.js` | مجموعة عمّال: تزامن بعدد العمّال، وطابور محدود (429 عند الامتلاء، 503 عند طول الانتظار)، ومهلة لكل طلب (504 مع استبدال العامل)، وإلغاء عند مغادرة المستخدم، وإعادة تشغيل تلقائية بتأخير متزايد، وحدّ لحجم الاستجابة، وتجاهل أي استجابة لا تخص الطلب. مؤشرات p50/p95/p99 بلا أي نص. |
| `backend/openmed/inference.js` | مجموعة واحدة لكل عملية تُضبط من `OPENMED_*`، وإغلاق نظيف عند إيقاف الخادم. |
| `backend/openmed/routes.js` | `Idempotency-Key`: إعادة الإرسال ترجع النتيجة الأولى دون تشغيل ثانٍ، والطلبان المتزامنان يُنفَّذ أحدهما فقط. حد طلبات لكل مستخدم (429 مع Retry-After). إلغاء التحليل إذا انقطع اتصال المستخدم. `/status` يعرض مؤشرات التشغيل وبصمة النسخة. |
| `backend/migrations/073_openmed_idempotency.sql` | إضافي فقط: عمود مفتاح منع التكرار وفهرس فريد جزئي. |
| `backend/openmed/fingerprint.js` | بصمة SHA-256 لملفات المساعد التي تحدد مخرجاته. تُعرض في `/status` وفي تقارير التقييم (`npm run clinical-ai:fingerprint`). |
| `backend/scripts/benchOpenmed.js` | أداة قياس، تفصيلها في القسم 4. |
| `backend/clinical-context/evalKit.js`، `scripts/clinicalEvalSplit.js`، `scripts/annotatorAgreement.js`، وتحديث `scripts/evalClinicalContext.js` | عُدّة التقييم المستقل، تفصيلها في القسم 5. |
| `docs/clinical-ai/ANNOTATION_GUIDELINE.md` | دليل الوسم للمختصين. |
| الواجهة | ترسل مفتاح منع تكرار مع كل ضغطة تحليل. |

ما تثبته الاختبارات:

**الحمل والتعطل** (`openmed-pool.test.js`، باستخدام عامل بديل بالبروتوكول نفسه):
- عملية واحدة تخدم عدة طلبات.
- التزامن يساوي عدد العمّال.
- الطابور الممتلئ يُرفض فوراً.
- الانتظار الطويل يُرفض.
- الطلب المعلّق يُقطع ويُستبدل العامل، ثم ينجح الطلب التالي.
- العامل المتعطل لا يُفشل إلا طلبه، ثم يعود.
- الإلغاء يُخرج الطلب من الطابور.
- الاستجابة الضخمة أو الغريبة لا تصل للمستخدم.
- المؤشرات ورسائل الخطأ لا تحتوي نص الطلب.
- الاختبارات مستقرة في ثلاث تشغيلات متتالية.

**بروتوكول العامل** (`tests/python/test_openmed_worker.py` بمحرك وهمي):
- النموذج يُحمَّل مرة واحدة عبر طلبات ونوافذ متعددة.
- ذيل النص الطويل يُحلَّل.
- الطلبات معزولة عن بعضها.
- الأخطاء رموز بلا نص.
- العربية مرفوضة.

**المسار الكامل مع قاعدة البيانات:**
- إعادة الإرسال بالمفتاح نفسه ترجع السجل الأول (200 مع ترويسة `Idempotent-Replay`)، وتشغيل واحد فقط.
- المفتاح نفسه بمدخل مختلف يرجع 409.
- الطلبان المتزامنان ينتجان سجلاً واحداً.
- حد الطلبات يرجع 429، ويتجدد الرصيد مع الوقت.
- انقطاع المستخدم يلغي التحليل ولا يحفظ شيئاً.

**تحقق حي** على الخادم المحلي ببيانات اصطناعية:
- الطلب الأول 201 والمكرر 200 بنفس السجل.
- `/status` يعرض مؤشرات المجموعة.
- **بصمة النسخة المنشورة مطابقة لبصمة الكود المختبر.**

## 4. قياس الأداء

الأداة جاهزة:

```bash
node scripts/benchOpenmed.js --workers 1,2 --concurrency 1,4,8 --requests 40 --sizes 300,3000,10000 --mode diseases --out bench.json
```

تقيس ما يلي:
- البدء البارد (من التشغيل حتى الجاهزية، مع تحميل النموذج).
- زمن أول طلب.
- p50/p95/p99 والإنتاجية ونسبة الخطأ لكل مستوى تزامن ولكل طول نص.
- ذاكرة كل عامل (الحالية والذروة) وزمن المعالج من `/proc`.
- زمن التعافي بعد قتل عامل: حتى أول إجابة، وحتى عودة العامل نفسه.
- بصمة النسخة ومواصفات الجهاز.

**التحقق من الأداة فقط** (`--simulate`): عامل بديل بزمن اصطناعي ثابت، ولا يوجد نموذج. تُظهر الأرقام أن الأداة تلتقط أثر الطابور: تزامن 4 على عامل واحد يرفع p50 نحو أربع مرات، وعاملان يخفضانه إلى النصف. **هذه الأرقام لا تصف أداء OpenMed ولا تصلح لتحديد عتاد.**

**المطلوب للقياس الحقيقي:**
- عدد المستخدمين المتزامنين المتوقع، وعدد التحليلات في ساعة الذروة، وطول النصوص المعتاد.
- حد زمن الاستجابة المقبول لكل استخدام.
- جهاز مماثل لجهاز الإنتاج، والنموذجان مثبتان.

بعدها تُشغَّل الأداة وتُحدَّد `OPENMED_WORKERS` و`OPENMED_MAX_QUEUE` و`OPENMED_TIMEOUT_MS` من النتائج. **لا نحدد مواصفات شراء أو SLA من أمثلة قليلة.**

## 5. التقييم اللغوي والسريري المستقل

**متعذر حالياً**، لأنه لا توجد نصوص من المستشفى يوسمها مختصون. العُدّة جاهزة ومختبرة:

1. **الوسم:** يُتبع `ANNOTATION_GUIDELINE.md`، وممارسان مستقلان يوسمان كل نص.
2. **الاتفاق بين المُعلِّمين:** `annotatorAgreement.js` يحسب Cohen's kappa لكل سمة، ويسرد الخلافات بالمعرّف فقط دون نص.
3. **التسجيل المسبق والتجميد:** `clinicalEvalSplit.js` يقسّم تقسيماً حتمياً بملح (salt) إلى dev وvalidation وtest، ويسجّل بصمة كل ملف وبصمة معايير النجاح في manifest.
4. **التشغيل النهائي:** المقيِّم يرفض مجموعة الاختبار في هذه الحالات:
   - بلا manifest.
   - إذا تغيّر الملف بعد التقسيم.
   - إذا تغيّرت المعايير عن المسجّلة.
   - دون تأكيد صريح.

   يسجّل كل تشغيل ويحذّر عند التكرار. يعرض النتائج **لكل لغة على حدة** (en وar وmixed)، مع فواصل ثقة وحجم العينة، ويقارنها بالمعايير المسجّلة مسبقاً. المعيار الذي بياناته غير كافية لا يُعد ناجحاً أبداً.
5. **التقرير:** يحمل بصمة الكود المختبر، وتُقارن ببصمة `/status` في النشر.

## 6. تدفق البيانات والصلاحيات

لا توجد مسارات بيانات جديدة:

- النص يصل إلى العامل المحلي عبر stdin كما كان.
- العامل لا يرث أسراراً، ويحجب الشبكة.
- مخرجات الأخطاء (stderr) تُهمل.
- المؤشرات وتقارير القياس والتقييم لا تحتوي نصاً سريرياً.
- مفتاح منع التكرار يُحفظ مع التحليل، وليس بياناً صحياً.

## 7. التشغيل والمراقبة والاسترجاع

| الإعداد | الافتراضي | الأثر |
|---|---|---|
| `OPENMED_WORKERS` | 1 | عدد العمّال. الذاكرة ≈ حجم النموذجين × العدد (تُقاس بالأداة) |
| `OPENMED_MAX_QUEUE` | 8 | طول الطابور قبل الرفض بـ429 |
| `OPENMED_QUEUE_TIMEOUT_MS` | 30000 | أقصى انتظار في الطابور |
| `OPENMED_TIMEOUT_MS` | 120000 | مهلة التحليل. بعدها يُستبدل العامل ويُعاد تحميل النموذج |
| `OPENMED_PRELOAD` | فارغ | تحميل النموذج عند البدء، مثلاً `diseases,medications` |
| `OPENMED_TORCH_THREADS` | 2 | خيوط المعالج لكل عامل |
| `OPENMED_RATE_PER_MINUTE` | 20 | حد التحليلات لكل مستخدم في الدقيقة، لكل نسخة خادم |
| `BUILD_COMMIT` | — | رقم الـcommit في البصمة |

- **المراقبة:** `/api/openmed/status` يعرض حالة العمّال، والطابور، ومرات الإعادة والتعطل والمهلة، والزمن p50/p95/p99، والبصمة.
- **التعافي:** تلقائي. إعادة التشغيل الكامل تكلّف زمن تحميل النموذج.
- **الاسترجاع:** إرجاع الكود يعيد السلوك السابق. الترحيل 073 إضافي فقط.

**قيود معروفة:**
- حد الطلبات وخريطة الطلبات الجارية داخل كل نسخة خادم. مع عدة نسخ يمنع الفهرس الفريد تكرار الحفظ، لكن الحد يصبح لكل نسخة.
- إلغاء تحليل جارٍ لا يوقف حساب النموذج؛ النتيجة تُهمل فقط.
- المهلة تقتل العامل، فيتكلف إعادة تحميل.
