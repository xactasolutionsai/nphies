# تشغيل إصلاحات المراجعة والتحقق من ربط نفيس

تعالج هذه النسخة ملاحظات المراجعة الـ26: حماية API والتحقق من JWT وصلاحيات الإدارة، تقييد حقول SQL وحقول المطالبات، المعاملات الذرية، حفظ وثيقة التأمين المختارة، منع الإرسال المتزامن، حفظ القيم المالية الصفرية، عزل التخزين والمسودات حسب المستخدم، HTTPS، معاملات البحث والعد، إبطال الذاكرة المؤقتة، سياسة إعادة المحاولة، أخطاء الاستطلاع، التحديث الجزئي للتفاصيل، فحص خدمة الأدوية، توحيد عناوين API والمحادثة، إنهاء SSE، انتهاء الجلسات، توقيت السعودية، إزالة تعريف الدالة المكرر، إعادة تحميل الاستعلامات، وإعداد lint واختبارات الانحدار.

## خطوات التشغيل

هذه الخطوات لقاعدة بيانات المشروع القائمة التي طُبقت عليها الترحيلات السابقة. لم تُطبّق ترحيلات على قاعدة الإنتاج ضمن المراجعة.

1. خذ نسخة احتياطية وأوقف الكتابة أثناء تحديث التطبيق وقاعدة البيانات.
2. من مجلد `backend` شغّل `npm ci`، واضبط اتصال قاعدة البيانات المستهدفة، ثم `npm run migrate-review`. يطبق الأمر الترحيلين `062_user_roles.sql` و`063_selected_coverage.sql` فقط. كلاهما قابل لإعادة التشغيل. يبقى عمود التأمين الرقمي القديم محفوظاً؛ لا يجري تخمين وثائق تاريخية أو تحويلها تلقائياً.
3. اضبط `JWT_SECRET` بقيمة سرية عشوائية خاصة لا تقل عن 32 محرفاً؛ لا تستخدم قيمة مثال. تغيير المفتاح يُلزم المستخدمين بتسجيل الدخول مجدداً.
4. امنح حساب المدير الموجود صلاحية صريحة: `npm run grant-admin -- admin@example.com` مع استبدال البريد بالحساب المطلوب. لم يعد البريد الثابت يمنح الإدارة تلقائياً.
5. ابنِ الواجهة من مجلد `frontend` باستخدام `npm ci` ثم `npm run build`. إعداد الإنتاج يستخدم `/api` من النطاق نفسه. اضبط وكيل HTTPS لتمرير هذا المسار إلى الخادم مع الحفاظ على `/api` في عنوان الطلب؛ ولمحادثة SSE عطّل buffering واضبط مهلة قراءة مناسبة. تغيير إعداد الواجهة وحده لا ينشئ شهادة TLS أو وكيلاً.
6. شغّل الخلفية بعد تطبيق الترحيلات والإعدادات. العملاء الخارجيون لواجهات التطبيق المحمية يحتاجون الآن `Authorization: Bearer <token>`.

## الحفاظ على ربط نفيس

- لم تُستبدل عناوين نفيس أو بيانات اعتماد المنشأة بعناوين جديدة، ولا يُرسل JWT الخاص بالتطبيق إلى نفيس.
- تُقارن 14 رسالة FHIR كاملة بمرجع من الكود قبل الإصلاح: خمسة أنواع موافقات وخمسة أنواع مطالبات والأهلية والإلغاء والاستطلاع والدفعات. بيانات المرجع اصطناعية، والوقت والمعرّفات العشوائية مثبتة للمقارنة.
- يتطلب اتصال الإنتاج HTTPS. إذا كانت بيئة OBA التجريبية المحددة لديك تدعم HTTP فقط، يلزم ضبط `NPHIES_ENVIRONMENT=sandbox` و`NPHIES_ALLOW_INSECURE_SANDBOX=true` صراحةً، واستخدام بيانات اصطناعية. لا تغيّر عنوان المزود تلقائياً إلى HTTPS دون دعم المزود له.
- تشمل الاختبارات عدم تكرار HTTP 400، وإعادة محاولة الأخطاء المؤقتة بنفس الرسالة، وحفظ المبالغ الصفرية، وربط الردود، وإظهار فشل معالجة الاستطلاع.
- اختبار PostgreSQL يجعل طلبي إرسال يقرآن المسودة في الوقت نفسه ويثبت خروج اتصال محاكى واحد فقط لكل من المطالبات والموافقات. ويختبر التراجع عن الحفظ عند فشل التفاصيل وحفظ وثيقة التأمين والتحديث الجزئي.

## إعادة التحقق

من `backend` شغّل `npm test`. لتشغيل اختبارات قاعدة البيانات أيضاً، اضبط `TEST_DATABASE_URL` إلى قاعدة PostgreSQL محلية منفصلة ينتهي اسمها بـ`_regression`. تنشئ الاختبارات مخططاً عشوائياً ببيانات اصطناعية وتحذفه بعد الانتهاء. تستخدم هذه الاختبارات جداول مختارة وترحيلات ذات صلة، وليست اختبار ترقية لكل مخطط الإنتاج.

من `frontend` شغّل `npm run lint` و`npm run build`.

التحقق المحلي لا يثبت قبول النظام الخارجي الحي: لم تُرسل معاملات حية إلى نفيس. قبل نشر الإنتاج، نفّذ اختبار قبول ببيانات اصطناعية في البيئة التجريبية المعتمدة مع إعدادات المنشأة الفعلية.
